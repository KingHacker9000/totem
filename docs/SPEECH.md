# Speech

Totem keeps speech local while delegating general-purpose reasoning to external agent providers.

## Pipeline

```text
microphone / keyboard
   -> browser push-to-talk or typed input
   -> local VAD
   -> local speech-to-text
   -> deterministic/mock task path OR configured AgentProvider
   -> durable Totem task
   -> response/result
   -> local text-to-speech
   -> browser/PC speaker
```

Keyboard input remains a first-class path so speech can be bypassed while debugging.

## Production PC baseline

The current PC speech baseline uses replaceable adapters rather than bundling native audio/model dependencies into Totem:

- **STT:** `whisper.cpp` through an external `whisper-cli` executable and model file.
- **TTS:** Piper through an external `piper` executable and model file.
- **Microphone input:** the dashboard `/speech` page uses the browser's microphone API for push-to-talk and sends PCM16 WAV data to core.
- **Speaker output:** `/speech` requests locally synthesized WAV from core and plays it through the browser/PC audio device.
- **Task routing:** speech and typed input converge on the same durable task gateway. `TOTEM_SPEECH_AGENT_PROVIDER=mock` keeps development deterministic; another configured AgentProvider id may be selected for real-provider use.

Totem does not download or bundle STT/TTS binaries or model weights. Operators install those separately and point Totem at them with configuration paths. Missing executables/models are reported as unavailable capability state instead of crashing core startup.

## Configuration

Core speech is disabled by default. The relevant environment variables are:

| Variable | Default | Meaning |
| --- | --- | --- |
| `TOTEM_STT_PROVIDER` | `none` | `none` or `whisper.cpp`. |
| `TOTEM_STT_EXECUTABLE` | unset | Path to the `whisper-cli` executable. |
| `TOTEM_STT_MODEL` | unset | Path to the local whisper.cpp model. |
| `TOTEM_TTS_PROVIDER` | `none` | `none` or `piper`. |
| `TOTEM_TTS_EXECUTABLE` | unset | Path to the Piper executable. |
| `TOTEM_TTS_MODEL` | unset | Path to the local Piper voice model. |
| `TOTEM_SPEECH_AGENT_PROVIDER` | `mock` | Durable task provider id used after text/transcription. |
| `TOTEM_SPEECH_VAD_THRESHOLD` | `0.015` | Energy VAD threshold from `0` to `1`. |

Example PowerShell configuration:

```powershell
$env:TOTEM_STT_PROVIDER = "whisper.cpp"
$env:TOTEM_STT_EXECUTABLE = "C:\Tools\whisper.cpp\whisper-cli.exe"
$env:TOTEM_STT_MODEL = "D:\TotemModels\ggml-base.en.bin"
$env:TOTEM_TTS_PROVIDER = "piper"
$env:TOTEM_TTS_EXECUTABLE = "C:\Tools\piper\piper.exe"
$env:TOTEM_TTS_MODEL = "D:\TotemModels\en_US-lessac-medium.onnx"
$env:TOTEM_SPEECH_AGENT_PROVIDER = "mock"
pnpm dev
```

Example Unix configuration:

```sh
TOTEM_STT_PROVIDER=whisper.cpp \
TOTEM_STT_EXECUTABLE=/opt/whisper.cpp/whisper-cli \
TOTEM_STT_MODEL=/srv/totem/models/ggml-base.en.bin \
TOTEM_TTS_PROVIDER=piper \
TOTEM_TTS_EXECUTABLE=/opt/piper/piper \
TOTEM_TTS_MODEL=/srv/totem/models/en_US-lessac-medium.onnx \
TOTEM_SPEECH_AGENT_PROVIDER=mock \
pnpm dev
```

Then open the dashboard's `/speech` route. Browser microphone permission is required only when using push-to-talk.

## Core API

The PC speech path is exposed through core-owned APIs:

```text
GET  /api/speech/status
POST /api/speech/text
POST /api/speech/audio
POST /api/speech/synthesize
POST /api/speech/barge-in
```

`/api/speech/status` reports adapter availability, model paths, active input/task state, last transcript, latency values, selected voice/model references, task provider, and VAD threshold. It never treats a missing local engine as a successful capability.

`POST /api/speech/audio` accepts base64-encoded PCM16 WAV generated by the PC/browser path. Raw microphone samples are processed ephemerally by the speech runtime and are not persisted as task data.

## Wake word

Push-to-talk is the production baseline for now. Wake-word detection remains an optional adapter seam and is intentionally not a blocker for the PC speech path. A future wake-word implementation should feed the same capture/runtime path rather than creating a separate assistant stack.

## Barge-in

Users must be able to interrupt speech immediately. TTS playback and active response streaming therefore use cancellable semantics rather than fire-and-forget audio. The `/speech` console exposes a barge-in/stop action backed by `POST /api/speech/barge-in`.

## Voice configuration

Voice selection belongs to theme/speech configuration, not to assistant capability. Themes may reference locally installed TTS voices/models while the speech service owns execution. A missing referenced voice/model must degrade visibly rather than silently granting a theme new capability.

## Privacy

Raw microphone audio is ephemeral by default. Recording/storage requires an explicit future opt-in feature with visible settings and retention controls.

## CI versus live validation

Credential-free CI uses deterministic process runners and speech fixtures. It validates adapter arguments, availability/failure normalization, WAV conversion, API routing, shared durable-task semantics, and barge-in behavior without requiring microphone hardware or model downloads.

The consolidated real-PC gate later exercises an installed STT model, installed TTS voice, browser microphone/speaker, and available real AgentProvider together. That live gate is intentionally separate from deterministic CI.

## Hardware migration

When Totem moves to Raspberry Pi 5, the speech/runtime contract remains the same while microphone/speaker drivers and selected physical hardware change. Acoustic echo cancellation, microphone/speaker placement, fan-noise mitigation, and physical mute behavior are validated during physical integration rather than hard-coded into the PC implementation.
